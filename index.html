The idea, in 30 seconds

  • Public by default is the problem. On a normal blockchain anyone can read balances, counterparties and history forever. That works for open markets and badly for real life.
  • Midnight splits the ledger. Midnight keeps a public state for what must be verifiable and a private state for what must stay yours, using zero-knowledge proofs — mostly generated on your own device.
  • Selective disclosure is the product. Prove “over 18”, “paid in full” or “this message is from me” without revealing the birth date, the amount, or the rest of the conversation.
  • NIGHT and DUST. NIGHT is Midnight’s token, held on Cardano; holding NIGHT generates DUST, the renewable resource that pays for shielded Midnight transactions.

8 · Commit now, reveal later — hash commitments

How do you prove you knew something earlier — a prediction, a sealed bid, a vote — without revealing it at the time? Publish a commitment: a hash of the secret now, the secret itself later. This makes a real SHA-256 hash computed locally on this device (the same idea as tool 6's commit-to-a-secret pattern) — your secret never leaves this page; only the hash is meant to be shared. Honest limits: a short or guessable secret can be brute-forced from its hash, so real systems add a long random salt — and this page's digest format is a teaching format, not Compact's on-chain persistent hash.

9 · What can an observer see? — public vs shielded

Pick an action and stand in the shoes of a stranger reading the ledger: what can they see, what stays private, and what still leaks anyway? This is a simplified teaching model of ledger visibility only — it does not model network-level metadata (timing, IP addresses) as solved, and every scenario names those residual leaks, because a private ledger is one layer of privacy, not the whole of it.

10 · Share a view, not your wallet — viewing-key scope simulator

Sometimes someone legitimately needs to check your shielded activity — an accountant, an auditor, a counterparty. The Midnight pattern is to disclose the narrowest scope that answers their question. Pick a scope and see what a viewer gets, what stays yours, and what to weigh first. This is a simplified teaching model of scoped disclosure in principle: exact viewing-key and disclosure capabilities depend on your wallet and the contract involved, so check the current Midnight docs before granting a real one. No key is entered, generated or connected here — never paste a real viewing key into a web page.

11 · Make it unguessable — secret strength & salt for commitments

Tool 8's honest limit, made measurable: anyone holding your commitment hash can guess at it offline, at machine speed, with nobody watching — so a commitment is only as safe as the secret behind it. Check a secret's strength here, then generate the standard fix: a long random salt. This is a rough teaching estimate, not a security audit: it assumes every character was picked uniformly at random from the character types you used, and human-chosen secrets are far more predictable than that model — words, names and dates fall to dictionary guessing long before brute force. The guessing rate used (10 billion a second) is a labelled assumption about a well-equipped offline attacker, not a measurement.

12 · Prove you're on the list — without showing the list

An allowlist, a voter roll, a set of eligible wallets: publish one short hash — the root — and the whole list is committed. Later, any one member can prove they're on it with a handful of sibling hashes, and a verifier who knows the root can check that proof without ever seeing the rest of the list. That structure is a Merkle tree, and the real SHA-256 for it runs locally here. Honestly labelled limits: a Merkle proof is not zero-knowledge — it reveals the entry itself, its position, the sibling hashes and (from the proof's length) the rough size of the list. The other entries stay behind their hashes, but a guessable entry can be checked by hashing a guess (tool 11's lesson), so real lists salt low-entropy entries. An odd entry at the end of a level is promoted unchanged, never duplicated. This page's hashed-message format is its own teaching format, not a specific chain's tree format — and nothing here connects to a chain or a wallet.

13 · Split a secret — no single share reveals it

Some secrets should not exist in just one place. Split a secret here and it is XORed with fresh random bytes generated locally, producing shares with a stark property: any share on its own is random bytes and reveals nothing about the secret's content, but all of them together rebuild it exactly. That is real secret sharing computed locally, not a simulation — the same one-time-pad maths that makes each incomplete set useless to whoever holds it. Honestly labelled limits: this is all-of-n sharing — every share is required, so losing one share loses the secret forever; real systems that need recovery use threshold (k-of-n) sharing such as Shamir's, where any k of n shares suffice — that scheme is named here, not implemented by this tool (tool 15 below implements it). A share is exactly as long as the secret, so a share's length leaks the secret's length. And never paste a real seed phrase or production secret into any web page, including this one — practise with throwaway secrets.

14 · Spend it once, stay private — notes & nullifiers

How does a shielded ledger stop you spending the same private coin twice, if it cannot see the coin? With two hashes of the note's secret, made for two different jobs. Creating a note publishes only its commitment hash. Spending it publishes a different hash — its nullifier — and the ledger's one mechanical rule is that a nullifier may appear only once, ever. Try it: create a note, spend it, then try to spend it again. This is a simplified teaching model of the note-and-nullifier idea, built from this page's own SHA-256 formats — it is not how a real Midnight note is constructed: real notes use random secrets and keys nobody can guess, plus a zero-knowledge proof that the note exists and the spender owns it. A human-chosen secret here can be dictionary-checked against both hashes (tool 11's lesson), and if it ever leaks, its commitment and nullifier become linkable after the fact. Never paste a real seed phrase or production secret into any web page, including this one — practise with throwaway secrets.

15 · Split with a safety net — any k of n shares (Shamir)

Tool 13's split has a hard edge: lose one share and the secret is gone. This is the threshold scheme it named — Shamir's secret sharing, computed locally for real. Each byte of your secret becomes the constant term of a polynomial over GF(256) whose other coefficients are fresh random bytes, and each share is that polynomial evaluated at a different point. Any k of the n shares rebuild the secret exactly by interpolation; k−1 shares are consistent with every possible secret, so they reveal nothing about its content. Honestly labelled limits: this is a teaching implementation, not an audited library — and there is no checksum, so with exactly k shares, one wrong or mistyped share rebuilds a wrong secret silently. A share is exactly as long as the secret, so a share's length leaks the secret's length. Never paste a real seed phrase or production secret into any web page, including this one — practise with throwaway secrets.

16 · Seal it so only they can read it — password-encrypted messages

A hash (tools 8, 12, 14) is one-way — nobody can un-hash it. Encryption is the opposite tool: reversible, but only for whoever holds the key. Seal a message here and it is encrypted for real, locally on this device, with AES-GCM: your password is stretched by PBKDF2 (210,000 rounds, a fresh random salt per seal) into the key, and the sealed text — safe to publish on its own — carries only the salt, the IV and the ciphertext. AES-GCM is authenticated, so a wrong password or one changed character fails to open instead of returning gibberish. Honestly labelled limits: this is a teaching implementation, not an audited encryption product, and its safety is exactly your password's safety — PBKDF2 slows offline guessing but cannot save a weak password (tool 11 measures that), and the sealed text's length reveals the message's approximate length. Send the password by a different channel from the sealed text: anyone with both can read it. Never paste a real seed phrase or production secret into any web page, including this one — practise with throwaway messages.

17 · Sign it — prove it came from you, without sharing your key

Encryption (tool 16) hides a message; a signature does the opposite job: the message stays public, but anyone can check that whoever holds one private key endorsed exactly these words — and that not one character changed since. This makes a real ECDSA key pair locally on this device, on the P-256 curve (the curve behind passkeys and WebAuthn; Bitcoin and Ethereum use its sibling curve secp256k1, which Web Crypto does not offer) and signs with ECDSA over SHA-256. The public key is safe to publish — it is how people recognise “you”. The private key IS the identity: anyone holding it can sign as you, with no recovery and no undo, so guard it exactly like a seed phrase. Honestly labelled limits: this is a teaching implementation, not an audited wallet; a signature does not hide the message, does not prove a legal name or real-world identity, and does not prove when the signing happened. Keys exist only in this page — nothing is stored or sent, and reloading loses the private key unless you saved it. Never paste a real wallet's private key into any web page, including this one — practise with throwaway keys.

18 · Agree on a secret nobody saw — key agreement

Sealing (tool 16) needs a password you already share, and signing (tool 17) proves who holds a key — but how do two people who have never met end up with a secret they both know and nobody else does, over a channel everyone can read? With key agreement — real ECDH on the P-256 curve, computed locally here: each side makes a key pair, the public keys are the only things exchanged, and each side mixes its own private key with the other's public key. Both sides land on exactly the same 32-byte shared secret, even though that secret is never exchanged and cannot be worked out from the two public keys alone. That handshake is what sits underneath private messaging. Honestly labelled limits: this is a teaching implementation, not an audited messaging app. Real systems never use the raw shared secret directly as a key — they run it through a key-derivation function first — and agreement alone does not prove who the other public key belongs to: a man-in-the-middle who swaps both public keys completes two separate agreements and can read everything, which is why real messengers let you compare a fingerprint of the secret, never the secret itself, over a channel you already trust. The secret is displayed on this page only so you can practise both sides in one place; a real app never shows it. Never paste a real wallet's private key into any web page, including this one — practise with throwaway keys.

19 · Stretch one secret into proper keys — key derivation (HKDF)

Tool 18 ends on a warning: real systems never use the raw shared secret directly as a key. This is the step that warning points at. Key derivation takes one secret and stretches it into separate, independent keys — one secret, many keys — but never the secret itself as a key. It runs locally for real here with HKDF (RFC 5869) over SHA-256: the purpose you pick is mixed into the derivation, so a different purpose means a different key — the messaging key, the storage key and the backup key from one secret share nothing usable, and leaking one reveals nothing about the others or the secret. An optional salt (tool 11's generator makes them) separates sessions: same secret, same purpose, different salt, different key. The salt is not a secret — both sides must pick the same purpose and the same salt, and they may exchange the salt openly. Honestly labelled limits: this is a teaching implementation, not an audited key-management product, and derivation does not strengthen a weak input — a guessable secret derives guessable keys, because anyone can run the same public derivation; HKDF assumes its input is already high-entropy key material, like tool 18's output, which is why there is deliberately no password stretching here. Never paste a real seed phrase or production secret into any web page, including this one — practise with throwaway secrets.

20 · Use the key — lock a message with the key you both derived

Tools 18 and 19 end with a key nobody has used yet — this is where it gets used. This tool uses the derived key directly as a real AES-GCM key: no password, no stretching and no salt, because tool 19's output is already high-entropy key material, which is exactly what the derivation was for. (Tool 16 is the contrast: it starts from a human password, so it must stretch it first, and its sealed text carries a salt. Here the sealed text carries only a fresh random IV per message.) Locking and opening run locally for real, and the authentication tag means a wrong key fails outright, exactly like a tampered or truncated message — there is no password fallback and no best guess. Honestly labelled limits: this is a teaching implementation, not an audited messaging app — real messengers add ratcheting, message numbering and key erasure on top of this shape. The key itself is the whole secret: whoever it leaks to reads everything locked with it, past and future, until both sides derive a fresh one, and the locked text still leaks the message's approximate length. Tool 24 below is the standard fix for that leak. Keys exist only in this page — nothing is stored or sent. Never paste a real wallet key or a production session key into any web page, including this one — practise with throwaway keys from tools 18–19.

21 · Know it's really from them — sign it, then seal it

Tool 20's seal has a gap worth naming plainly: AES-GCM proves the key, not the person. Anyone who holds the session key can seal a message in anyone's name, and whoever opens it cannot tell — the seal checks out, the words look right, and the sender is whoever the opener assumes. This tool closes the gap the way real messengers do: the signature goes inside the seal. The sender signs the message with their tool-17 signing key first, then seals message and signature together with the session key. The opener opens the seal, then checks the signature against the sender's public key — and the two answers stay separate: a message can open perfectly and still fail the signature check, in which case the words are shown but flagged, because private is not the same as from them. Honestly labelled limits: this is a teaching implementation, not an audited messaging app. The signature proves the signing key, not a legal name, and it only means anything if the public key really is the sender's — get it from them somewhere a swap would be visible, the tool-18 lesson. Never paste a real wallet's private key into any web page, including this one — practise with throwaway keys from tools 17–19.

22 · One key per message — the ratchet

Tool 20 names the price of one key for everything: whoever it leaks to reads everything locked with it, past and future. This tool builds the fix real messengers use — a ratchet — in its simplest symmetric form: one fresh key per message, and the key moves on the moment it has been used. A chain state is one line, p4a-chain-v1:<position>:<chain key>, starting from a tool-19 session key at position 0. Each step runs HKDF (tool 19's machinery) twice over the chain key with two different labels: one output is this message's own key, sealing through tool 20's exact format, and the other is the next chain key. HKDF runs one way only, so there is no way to recompute an earlier message key from a later state — overwrite an old state and its messages are gone for good, even to someone who later gets your current state. That is forward secrecy for the past. The honest limits are the other half of the lesson: this chain protects the past only — a leaked current state opens every message after it, until both sides agree fresh keys with tools 18–19 and start a new chain; messages open strictly in order, because this simple chain keeps no skipped-message keys — tool 25 below adds that store, with numbered seals; each direction needs its own chain, started from a different tool-19 purpose or salt; and a chain stops at a labelled cap of 1,000,000 messages rather than running unbounded. A failed open advances nothing, so an early message can be retried when its turn comes. Honestly labelled: this is a teaching implementation, not an audited messaging app — real messengers add a second, asymmetric ratchet on top, which is what heals a chain after a leak — tool 23 below builds a simplified version of that healing step, done by hand. Never paste a real wallet key or a production session key into any web page, including this one — practise with throwaway keys from tools 18–19.

23 · Heal the chain — a fresh agreement restarts the ratchet

Tool 22's chain protects the past and says so plainly: a leaked current state opens every message after it, until both sides agree fresh keys. This tool is that recovery, done by hand — a simplified version of the second, asymmetric ratchet real messengers run automatically. Both holders of one direction's chain make brand-new agreement pairs with tool 18 and swap the public keys openly — public keys need no secrecy, though they still need to really be each other's (tool 18's fingerprint check). Each side mixes the fresh shared secret — which only the two new private keys can produce — with the chain key they both already hold: the secret goes into HKDF as the input, the current chain key as the salt, under its own label. The result is a new chain at position 0 that someone holding only the leaked state cannot follow them to: they have the old chain key, but without a new private key they cannot compute the fresh secret, and the healed key exists nowhere until both ingredients meet. The honest limits: healing protects only what comes after it — it does not unlock the past, reopen deleted messages, or help while a leak is still live on a compromised device; both sides must heal from exactly the same current state, or their healed chains differ and seals simply fail; and one manual heal is a teaching simplification of a step real apps do on every reply. Honestly labelled: this is a teaching implementation, not an audited messaging app. Never paste a real wallet key or a production session key into any web page, including this one — practise with throwaway keys from tools 18–19.

24 · Hide the length — pad it to one size before sealing

Every seal on this page is honest about the same leak — tools 13, 15, 16 and 20 all name it: a sealed text's length tracks the message's length, so a relay, a ledger watcher or a curious server learns roughly how much was said without reading a word. A one-word answer, a four-figure amount and a long confession seal to visibly different sizes: the length itself is the leak. The standard fix is padding, and that is what this tool does for real: the message is padded up to a fixed bucket size before it is locked — an 8-byte header (a "P4AP" marker plus the message's true byte length) goes in front of its UTF-8 bytes, fresh random bytes fill the rest, and the whole block, exactly 256, 1,024, 4,096 or 16,384 bytes, is locked with AES-GCM under a tool-19 session key, in its own p4a-paddedseal-v1 format. The padding sits inside the lock, so the authentication tag covers the filler too: changing any of it fails outright. Two messages in the same bucket produce locked lines of exactly the same length; the opener reads the true length back from the header and the filler is never shown. The honest limits: padding hides length only inside a bucket — which bucket a message landed in still shows; timing and frequency are untouched, and a watcher who sees many messages can still learn from the pattern; and real messengers pad inside a ratcheted protocol with cover traffic on top. Honestly labelled: this is a teaching implementation, not an audited messaging app. Never paste a real wallet key or a production session key into any web page, including this one — practise with throwaway keys from tools 18–19.

25 · Out of order, still private — skipped message keys

Tool 22's ratchet is honest about its limit: it opens messages strictly in order, because it keeps no store for skipped message keys. Real networks do not deliver in order — a message is delayed, retried or routed another way — and real messengers answer with a skipped-key store, the way Signal's protocol does. This tool builds it. The seal carries its position on the outside, p4a-oooseal-v1:<position>:<iv>:<cipher> — tool 20's exact AES-GCM seal under that position's ratchet key, numbered, so the receiver knows which key it needs. When the message for position 5 arrives while your chain sits at 3, the chain steps forward, the keys for 3 and 4 go into a small store (p4a-skipped-v1), and 5 opens now; when 3 and 4 finally arrive, their stored keys open them — and each stored key is erased the moment it is used, so a late message opens exactly once and a replay finds no key and a chain that has already passed it. The store is bounded on purpose: at most 32 keys kept, and one open will not step the chain more positions than the store could hold the skipped keys for — warehousing keys for messages that may never arrive is the denial-of-service shape real protocols cap for the same reason, and a refusal consumes nothing, so the message can be retried once the gap closes honestly. The honest limits: a stored key is a past message's whole secret kept alive past its turn — forward secrecy for those positions is paused, not held, until the late message arrives and the key is erased, and someone who copies the store reads exactly the messages it holds keys for; the position on the outside is metadata a watcher can see, like tool 24's bucket; and this is still the symmetric chain, so tool 23's heal remains the answer to a leak. Honestly labelled: this is a teaching implementation, not an audited messaging app. Never paste a real wallet key or a production session key into any web page, including this one — practise with throwaway keys from tools 18–19.

26 · For their key only — a sealed box anyone can close, only they can open

Every seal before this one needs something shared in advance: tool 16 a password both sides know, tools 20–25 a session key both sides derived together in tool 18's live, two-sided agreement. This tool serves the most ordinary case those leave out — sending something private to someone who is not there. They published a public key, and that is all you have. It is the sealed-box pattern behind “encrypt to their public key”: anyone who knows your public key can close a box for you, and only the matching private key opens it — no handshake and no shared password. Closing a box makes a fresh, one-message agreement pair, mixes it with the recipient's public key (tool 18), stretches the result once with HKDF — the one-message public key itself as the salt, so this box's key is bound to this box alone — and seals with tool 20's AES-GCM, in one versioned line: p4a-box-v1:<ephemeral public key>:<iv>:<cipher>. The ephemeral public key rides on the outside in plain view because it is not a secret: the recipient mixes it with their private key, lands on the same secret, re-derives the same key and opens; anyone else lands on a different secret and the seal refuses. The one-message private key is never stored, shown or sent — once the box is closed it has done its only job. The honest limits: a box proves nothing about who sent it — the recipient's public key is public, so anyone can close a box in anyone's name, and tool 21's signature inside a seal is this hub's answer when the sender matters; there is no ratchet here, so if your private key is copied later, every box ever closed to it opens — forward secrecy belongs to tools 22–25, whose keys are erased as they are used; and a public key only protects you if it really is theirs, because a swapped key closes every box to the swapper instead. Honestly labelled: this is a teaching implementation, not an audited messaging app. Never paste a real wallet key or a production private key into any web page, including this one — practise with throwaway keys from tool 18.

27 · A box that names its sender — sign it, then close it in the box

Tool 26's sealed box serves the person who is not there, and names its own limit in the same breath: a box proves nothing about who sent it, because the recipient's public key is public and anyone can close a box in anyone's name. Tool 21 is this hub's answer when the sender matters — a signature inside a seal — but it needs a session key both sides derived together, which is exactly what the box case does not have. This tool puts the two together: sign it, then close it in the box. The sender signs the message with their signing key (tool 17), and the signature rides inside the box in the same signed envelope tool 21 uses — inside, so only the recipient ever sees it, and a watcher cannot even tell this box is signed. The envelope is then closed exactly like tool 26's box — a fresh, one-message agreement pair (tool 18), HKDF stretched once, AES-GCM (tool 20) — with two deliberate separations: the stretching step uses its own label, so signed and plain boxes derive unrelated keys from the same secret, and the line gets its own format, p4a-authbox-v1:<ephemeral public key>:<iv>:<cipher>, so neither box can be relabelled into the other — a relabelled line fails closed at the seal before any envelope is read. Opening keeps tool 21's honest split: opening and verifying are two separate answers, so the box can open perfectly while the name does not check out — that result is shown with its message, not hidden. The honest limits are inherited from both parents: the signature proves the signing key, not a legal name; both public keys have to really be theirs — a swapped recipient key hands every box to the swapper, and a swapped sender key makes a stranger's signature verify under the wrong name; there is still no ratchet, so if the recipient's private key is copied later, every signed box ever closed to it opens, signatures and all; and a copied box line opens again — nothing inside proves when it was signed or that it was sent only once, so freshness is the application's job, not the box's. Honestly labelled: this is a teaching implementation, not an audited messaging app. Never paste a real wallet key or a production private key into any web page, including this one — practise with throwaway keys from tools 17 and 18.

28 · Is that really their key? — the safety number

Every tool from 17 on ends on the same warning: a signature, a sealed box, an agreement — all of them prove the key, and the key only helps if the public key you hold is really theirs. The swap that defeats the whole suite happens before any message: a directory, a profile page or a person in the middle hands you a different public key, and from then on every check passes — against the swapper's key. This tool is the check that runs before trust: a safety number for a pair of public keys. Both keys are sorted and hashed together under a domain label, so both people compute exactly the same number from the same two published keys, in either order, without meeting and without any secret. The number is built from public keys alone, so it is safe to read aloud, print or post, and revealing it reveals nothing about any private key. Twelve groups of five digits — long enough that a swapper cannot realistically find a key that lands on the same number, short enough to compare over a phone call. One rule matters more than the maths: compare it over a channel you already trust — a voice you recognise, in person — because a number delivered over the same channel that delivered the key proves nothing; the swapper swaps both. If even one group differs, stop: one of the keys is not the key its owner published, and no message should be sent until the keys are re-checked on a trusted channel. The honest limits: the number proves the keys, not a legal name — it binds a key to whoever read the number to you, and to nothing else; it must be re-compared whenever a key changes, because a new key is a new number; this page's digit format is its own teaching format (the first 60 hex characters of a SHA-256 digest, five hex characters to a five-digit group), not any messenger's published safety-number format; and a 60-digit number is a truncated hash, so collision resistance here is a practical teaching property, not a proof. Honestly labelled: this is a teaching implementation, not an audited identity system. This tool takes public keys only — never paste a real wallet key or any private key into any web page, including this one; practise with throwaway keys from tools 17 and 18.

29 · A fresh destination for every payment — one-time destinations

Every tool before this one protects the content of a message or the fact behind a proof. This one protects the address itself. Publish one address and reuse it for every payment, and anyone watching the ledger can total what you received, see when, and link every payer who ever used it — no decryption needed, because the link is the address. The stealth pattern answers with a fresh destination for every payment. The sender makes a one-payment agreement pair (tool 18), mixes its private half with the recipient's published public key, and hashes the shared secret under this tool's own label: that digest is the destination — a fresh identifier nobody can connect to the published key from the outside. The one-payment public key travels with the payment in plain view, because it is not a secret: the recipient scans with it, mixing their private key with it to land on the same secret, the same hash, the same destination — and a match means “this one is mine”. Two payments to the same person produce two unrelated destinations, because each rides on a fresh pair; the one-payment private key is never stored, shown or sent. The honest limits: this is a teaching model of the recognition half of stealth addressing — real schemes derive a one-time public key on the curve, so the recipient also derives the matching one-time private key that spends; here the destination is an identifier computed from the shared secret, it is not an address on any chain, and nothing here moves or holds funds. Tool 30 below builds the spend half this one leaves out — the one-time public key derived on the curve itself, and the matching one-time private key. The sender necessarily knows the destination they made — unlinkability here is against outside watchers, not against the payer. Scanning needs the one-payment key that travelled with the payment: lose it and that destination can no longer be recognised. And a fresh destination hides who was paid, not that a payment happened — amounts, timing and network-level metadata still leak (tool 9's lesson). Honestly labelled: this is a teaching implementation, not an audited wallet. Never paste a real wallet key or a production private key into any web page, including this one — practise with throwaway keys from tool 18.

30 · The key that can spend it — one-time spend keys

Tool 29 ends on a gap it names itself: it models the recognition half of stealth addressing, where the recipient can spot a payment as theirs, but real schemes — Monero-style, EIP-5564-style — also derive a one-time public key on the curve, so the recipient also derives the matching one-time private key that spends. This tool builds that spend half, with real P-256 curve arithmetic computed locally — plain integer maths on the curve's published parameters, no library and nothing sent anywhere. The shared secret (tool 18) is hashed once under this tool's own label, privacy4all-spendkey-v1; that digest, read as a number under the curve order, is the tweak. The sender adds tweak×G to the recipient's published point — that sum is the one-time public key. The recipient adds the same tweak to their private number instead, and the curve's own arithmetic does the rest: (r + t)×G is r×G + t×G, the same point, so the tweaked private key matches the one-time public key exactly — and nobody else can derive either side, because the tweak needs the secret and the secret needs a private key. The keys stay in this hub's formats throughout: the one-time public key is a 91-byte key exactly like tool 18's, and the one-time private key is a 138-byte key rebuilt around the tweaked number, so the other tools here can read it like any practise key. The honest limits: the key is still not an address on any chain and nothing here moves or holds funds — this is the derivation half of the pattern, shown on the P-256 curve this hub's practise keys use (real stealth schemes run on their own curves and encodings, and their exact tweak hashes differ); whoever holds the recipient's ordinary private key plus the one-payment public key can derive the spend key — that is the design — so a copied private key endangers every payment ever sent to it, exactly as tool 29 warned for recognition; and the curve code is written to be read and checked line by line, not for speed or side-channel resistance — production wallets use audited, constant-time libraries. Tool 31 below answers the other flaw this tool shares with tool 29 — the key that scans being the key that spends — by splitting the published pair in two: a view key that can watch, and a spend key that can spend. Honestly labelled: this is a teaching implementation, not an audited wallet. Never paste a real wallet key or a production private key into any web page, including this one — practise with throwaway keys from tool 18.

31 · Eyes without hands — a view key that can watch but never spend

Tools 29 and 30 share one honest flaw, and both name it: the key that scans for payments is the key that spends them. Recognising a payment takes the recipient's private key, and claiming its spend key takes that same key — so a bookkeeper, an auditor, a watch-only wallet on a phone, or a family member who should be able to see what arrived can only be helped by handing over the power to take it. Real stealth schemes — Monero-style — split the job in two, and this tool builds the split: publish a view key pair and a spend key pair side by side (two tool 18 pairs). Senders mix with the view public key, so whoever holds the view private key — and only them — can re-derive every payment's secret, land on its destination under this tool's own label privacy4all-viewscan-v1, and name its one-time public key, because the spend public key is public. Watching is complete. Spending is not: the tweak (this tool's second label, privacy4all-viewspend-v1) is added to the spend private number, and the view holder does not have that number — adding the tweak to the view number instead derives a well-formed key that matches nothing. Claiming a spend key therefore takes both private keys: the view key finds the tweak, the spend key uses it. The split cuts both ways: the spend private key alone cannot even scan in this construction, so losing the view key means losing sight of payments until it is recovered; and the view key is still a secret worth guarding, because its holder sees every payment this published pair ever receives — past and future — until the keys rotate: a view key is eyes without hands, not eyes that see nothing. The honest limits: the destination and the keys are still not an address on any chain and nothing here moves or holds funds — this is the derivation pattern on the P-256 curve this hub's practise keys use, and real schemes differ in curves, encodings and hash choices. Honestly labelled: this is a teaching implementation, not an audited wallet. Never paste a real wallet key or a production private key into any web page, including this one — practise with throwaway keys from tool 18.

32 · Prove you know the key — a zero-knowledge proof of knowledge

Tool 5 above simulates the zero-knowledge pattern and says so in so many words — a teaching simulation, not a cryptographic proof. This tool runs a real one: the Schnorr identification protocol, the classic proof of knowledge that modern zero-knowledge systems grow from, computed locally on the same P-256 curve as tools 17, 18 and 30. Say you need to convince someone you hold the private key behind a published public key — without revealing the key, and without signing anything (tool 17's signatures bind a message and can be shown around forever; a proof answers one fresh question, once). It takes three moves, and the order is the security. First, the commitment must be fixed before the challenge is chosen: you pick a fresh secret nonce, publish only its public half as the commitment, and keep the nonce in a prover-only state line. Second, the verifier — only now — draws a fresh, unpredictable challenge number; a challenge of zero is refused, because with zero the answer is just the nonce and proves nothing about the key. Third, you answer with a single number blended from the nonce, the challenge and your private key, and the verifier checks one curve equation against your public key: it balances only if the answer was genuinely built from the private number, yet the answer itself reveals neither secret — one equation, two unknowns. The two ways it breaks are plain: a prover who sees the challenge first can work backwards and fake the whole proof for a key they do not hold, which is why the commitment coming first is the proof and not ceremony; and answering two challenges with the same commitment leaks the private key itself — two answers differ by a multiple of it that anyone can divide out — so one state answers exactly one challenge and is then thrown away. A completed proof is not a signature: it signs no message and authorises nothing, and it proves knowledge of the private key, not a legal name — the key could be anyone's, borrowed or stolen; what is proved is that the answerer holds it, against this challenge, now — an old answer replayed against a new challenge simply fails. The honest limits: this one page plays both sides, so it demonstrates the maths, not a live exchange — across a real exchange the ordering is enforced by who speaks when; this is the identification protocol in the open, not one of Midnight's Compact circuit proofs, which hide whole computations rather than one key; and like tool 30 the curve code is a teaching implementation — affine arithmetic written to be read and checked line by line, not an audited wallet and not side-channel resistant. Never paste a real wallet key or a production private key into any web page, including this one — practise with throwaway keys from tools 17 and 18. Tool 33 below takes the verifier out of the room: the challenge is hashed from the message and the commitment together, and this same proof becomes a signature anyone can check.

33 · A proof that signs itself — a Schnorr signature

Tool 32 above runs a real proof of knowledge, and names its own limit in so many words: a completed proof is not a signature — it needs a verifier in the room, drawing a fresh challenge by hand, and it convinces that one verifier, once. This tool takes the verifier out of the room, with the trick that turns the identification protocol into a signature scheme — the Fiat–Shamir transform. The challenge is no longer drawn by anyone: it is hashed, with SHA-256 under this tool's own label, from the commitment and the message together. The commitment still comes first — it is an input to the hash, so the challenge cannot exist before the commitment is fixed, and the backwards forgery tool 32 demonstrates stays impossible — but the signer can now compute the challenge alone, answer it with exactly tool 32's arithmetic, and publish the commitment and the answer as one signature line. Anyone, anywhere, at any later time, rehashes the challenge from the message and checks the same equation against the public key: it balances only if the line was built from the private key behind that key, over exactly that message — change one character and it fails. What is gained is what tool 32 gives up, and what is lost is what tool 32 keeps. A signature binds a message and can be shown around forever, which is the point — and the cost: it proves the key signed that message, to anyone, and says nothing about the holder being present now; tool 32's freshness is deliberately traded for transferability. The nonce rule does not soften in the trade: one nonce behind two signatures leaks the private key itself, because the two answers differ by a multiple of it that anyone can divide out — so this tool draws a fresh nonce for every signature, and signing the same message twice produces two different lines that both check out. The honest limits: this is a real Schnorr signature, computed and checked locally, but it is not the signature format any chain or wallet checks — tool 17's ECDSA remains the signature a P-256 wallet would produce, and real Schnorr deployments such as Bitcoin's BIP-340 use their own curves, encodings and hash constructions; like tool 32 this is the identification protocol's maths in the open, not one of Midnight's Compact circuit proofs; and like tool 30 the curve code is a teaching implementation — affine arithmetic written to be read and checked line by line, not an audited wallet and not side-channel resistant. Never paste a real wallet key or a production private key into any web page, including this one — practise with throwaway keys from tools 17 and 18. Tool 34 below turns the same arithmetic to a different question: not “was it this key?” but “was it one of these keys — proved, without saying which?”

34 · One of us signed it — a ring signature

Tools 17 and 33 prove a statement came from one named key — and naming the signer is sometimes exactly what you do not want. Say a statement should carry weight because it came from inside a group — a maintainer, an auditor, an employee — while the person who actually signed stays unnameable. This tool runs the construction built for that: a ring signature, in the classic Abe–Ohkubo–Suzuki form, computed locally on the same P-256 curve as tools 17, 18 and 30. The signer chooses a ring of public keys — their own among them, the rest borrowed from anyone whose key is published — and signs once, for the whole ring. The machinery is a chain of tool 33's hashed challenges closed into a loop: each member contributes one link built from an answer and that member's key, each link's challenge is hashed from the link before it, and the loop must come back to its own seed. The signer alone can close it, because they invent the other members' answers forwards from random numbers — no private key needed for a link you build in that direction — walk the chain around the ring, and answer the one challenge the chain finally hands their own position, with the only private key used anywhere in the signature. A verifier walks the same chain and learns the loop closed: exactly one of these keys signed this message — and it never says which one. Not “cannot easily tell”: the signer's answer is algebraically indistinguishable from the invented ones around it, so every member is an equally good suspect from the signature alone, and no amount of later computing changes that. The limits are stated as plainly as the promise. The ring is the whole anonymity set, so size is safety: with two keys the ambiguity is a coin flip, and this page caps the ring at six keys, a practicality limit rather than a strength claim. Nobody in the ring had to agree to be in it — the signer assembles the ring from published keys alone, and the other members need not know, consent, or have any connection to the statement — so a ring signature is not a group endorsement, and borrowing a well-known key into a ring lends a statement none of that key's authority; it proves one of the listed keys signed, full stop. This teaching version carries no key image, so two signatures from the same signer cannot be linked by the signatures alone — a deliberate omission, named here because real deployments choose the other way on purpose: Monero, the best-known ring signature system, adds a key image precisely so one member cannot spend the same note twice undetected. And the honest frame around all of it: this is a real ring signature computed and checked locally, but it is not the signature format any chain or wallet checks; it is the maths in the open, not one of Midnight's Compact circuit proofs; and like tool 30 the curve code is a teaching implementation — affine arithmetic written to be read and checked line by line, not an audited wallet and not side-channel resistant. Never paste a real wallet key or a production private key into any web page, including this one — practise with throwaway keys from tools 17 and 18. Tool 35 below makes exactly the trade this tool declines: it adds the key image, so the same signer acting twice can be caught — without ever being named.

35 · Signed twice? It shows — a linkable ring signature

Tool 34 above ends on a deliberate omission, named in its own text: it carries no key image, so two of its signatures by the same signer cannot be linked by the signatures alone — and real deployments choose the other way on purpose, because some statements must be made exactly once. A note that can be spent, a vote that can be cast, an attestation that can be claimed: if the same key can sign twice in perfect deniability, double-spending and double-voting are undetectable. This tool makes the other choice, in the LSAG form of tool 34's ring, computed locally on the same P-256 curve. Every signature now carries a key image: a second curve point bound to the signer's key alone, built as the private key times a hash of the signer's public key onto the curve. That hash-to-point is built by try-and-increment — hash the key under this tool's own label with a counter, read the digest as an x coordinate, keep the first x that lands on the curve — so the point it lands on has no known discrete log, and that is load-bearing: nobody can compute a member's key image from their public key alone, run down the ring matching images to names, and unmask the signer. The chain doubles to carry it: each member's link is now a pair of points, the second walking the hash points and the image exactly as the first walks the generators and the keys, and each challenge hashes both points with the message. The signer closes the loop the way tool 34 does — invent the other answers forwards, answer the final challenge with the one private key in play — and the loop closes on both points at once only because the image really is that key's image. What a verifier gains is narrow and exact: the signature is genuine, one of the ring signed — and the image can be compared. Two lines carrying the same image came from the same key, in whatever rings, over whatever messages. What that costs is stated as plainly as what it buys. Linkability is privacy given up on purpose: in this teaching version the image is tied to the member key itself, so the same signer is linkable across every ring and every message they ever sign here — Monero, the best-known user of this construction, ties its image to a one-time key per note, so only spending the same note twice links, a narrower exposure than this page's. And linked is not identified: a matched image proves one key acted twice and still never says which member it was — the anonymity inside each single signature survives intact; what dies is the claim that two signatures were strangers. The honest frame around all of it: this is a real linkable ring signature computed and checked locally, but it is not the signature format any chain or wallet checks; it is the maths in the open, not one of Midnight's Compact circuit proofs; and like tool 30 the curve code is a teaching implementation — affine arithmetic written to be read and checked line by line, not an audited wallet and not side-channel resistant. Never paste a real wallet key or a production private key into any web page, including this one — practise with throwaway keys from tools 17 and 18. Tool 36 below turns the whole question around: tools 33 to 35 vary who the signature names, but every signer in them sees the message — the next tool's signer never does.

36 · Signed without seeing — a blind signature

Every signer in tools 17 and 33 to 35 sees what they sign — the message sits inside the hash. Some signatures only work if the signer never does. A token, a voucher, an anonymous credential is worth having precisely because the authority who issued it cannot recognise it when it comes back: if they could, the day it was issued and the day it is spent would link, and the holder's privacy would be gone. David Chaum's answer is the blind signature, run here in its Schnorr form, locally on the same P-256 curve as tools 17, 18 and 30, as a four-move exchange that mirrors tool 32 with the requester standing between the signer and the message. Move 1 is the signer's, and needs no key at all: a fresh nonce and its commitment, exactly tool 32's first move, the nonce kept in a signer-only state line. Move 2 is the requester's alone: two secret blinding factors shift the commitment to a final commitment the signer never sees, the real challenge is hashed out of that shifted commitment and the message with tool 33's own challenge, and the signer is sent only the blinded challenge — one number, carrying no trace of the message, the final commitment, or the real challenge. Move 3 is tool 32's answer unchanged, the one place a private key is used: the signer answers a challenge they cannot read. Move 4 is the requester's finish: the answer is lifted by the first blinding factor and published as an ordinary p4a-schnorr-v1 line — checkable in tool 33's verify form above, against the signer's key and the exact message, where it balances. The signer did sign that message; the algebra says so. They simply never saw it, and the line carries neither blinding factor, so nothing in it points back to the signing session that produced it. The dangers are stated as plainly as the promise, because blindness cuts both ways. The signer is endorsing sight unseen: a blind-signing key must only ever sign for a service whose blinded challenges are worth honouring whoever presents them — tokens, vouchers, ballots — never for statements, because a blinded challenge can hide any message at all, including one the signer would refuse in the open. The nonce rule sharpens rather than softens: one nonce behind two blinded answers leaks the private scalar exactly as in tools 32 and 33, and a signer answering many sessions in parallel faces the ROS attack on blind Schnorr — real deployments answer one session at a time, bind each commitment to a single session, or use constructions built to resist it; this page does none of that coordination for you, and says so. And the requester's side has its own secret to keep: leak the two blinding factors beside the published line and anyone can walk back to the session's blinded challenge — the unlinkability is only as good as their secrecy, which is why the request state line is never published. The honest frame around all of it: this is a real blind signature computed and checked locally, but it is not the signature format any chain or wallet checks; it is the maths in the open, not one of Midnight's Compact circuit proofs; and like tool 30 the curve code is a teaching implementation — affine arithmetic written to be read and checked line by line, not an audited wallet and not side-channel resistant. Never paste a real wallet key or a production private key into any web page, including this one — practise with throwaway keys from tools 17 and 18.
